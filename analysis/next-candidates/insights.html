모바일 웹뷰 신규 DS 인사이트

1군, 2군 후보 8개 시스템의 소스를 병렬 실측한 결과에서 신규 디자인 시스템 설계 지침을 추출했다.

근거: 시스템별 상세 문서 8건(baseweb · primer · mantine · semi · antd-mobile · seed · abc-def · vkui) · 고정 커밋: sources-candidates/MANIFEST.md · 분석일 2026-08-13

결론 요약

1. 진짜 모바일 시스템은 3개뿐이다. antd-mobile, Seed, VKUI만 mobile-first다. Semi Design과 ABC Def는 문서상 표방과 달리 실측으로는 데스크톱 전용이다. 분류는 문서가 아니라 소스 신호(safe-area, hover, 터치 타깃)로 해야 한다.

2. "primitive는 직교 축, use-case는 별도 컴포넌트"가 8개 중 7개 시스템의 합의다. Seed만 한발 더 나가 범용 Button을 없애고 ActionButton부터 시작한다. 신규 DS는 중간 지점이 안전하다: primitive를 유지하되, use-case 계층을 1급으로 둔다.

3. 모바일 3사가 독립적으로 수렴한 기반 5종이 있다. safe-area 전역 변수, pressed 1급 상태(hover 가드), 정적 CSS + CSS 변수 + html 속성 테마, 오버레이 혈통 구조, 44px급 터치 타깃. 이 5종은 논쟁 없이 채택한다.

신규 DS에 적용할 판별 체크리스트

외부 시스템을 참고하거나 컴포넌트를 이식할 때 이 5개를 먼저 확인한다.

  • safe-area 처리가 전역 계층에 있는가 (env(safe-area-inset-*) 참조 위치)
  • hover가 가드 없이 쓰였는가 (생 :hover 개수)
  • 기본 컨트롤 높이가 44px 이상인가
  • 터치 제스처(드래그, 스와이프, 당겨서 새로고침)를 시스템이 소유하는가
  • 바텀시트, 탭바, 내비바가 1급 컴포넌트인가

2. 토큰 아키텍처: 3계층이 합의, 차이는 상태의 위치

8개 전부 사실상 3계층(원시 팔레트 → 시맨틱 → 컴포넌트)이다. 논점은 계층 수가 아니라 눌림 상태를 어디에 두느냐다.

시스템계층상태(-pressed 등)의 위치전달 방식
Seedpalette → semantic → component (Figma→YAML→생성)semantic 토큰에 -pressed 쌍 내장 (bg.brand-solid-pressed)CSS 변수 + html data 속성
VKUI원시 JSON → 시맨틱 TS → 테마 상속(69종)토큰 값 자체에 hover/active와 밀도(regular/compact) 내장CSS 변수, 루트 클래스 교체
antd-mobileglobal(--adm-*) → 컴포넌트 공개 변수 → 인스턴스 변수:active 셀렉터 처리, 인스턴스 변수는 타입으로 계약정적 CSS + CSS 변수
Primerbase → functional → component (테마 14종)셀렉터 처리. coarse/fine 타깃 토큰 이원화가 특징CSS 변수 + data 속성

권고. 3계층(palette → semantic → component)을 채택한다. semantic 계층에 Seed처럼 -pressed 쌍을 내장한다. hover 쌍은 만들지 않는다. 전달은 정적 CSS + CSS 변수 + html data 속성으로 한다. 런타임 CSS-in-JS는 배제한다(8개 중 Base Web만 사용하며, 성능과 이식성 모두 불리). component 토큰은 ABC Def처럼 자동 생성 파일 1개로 모아 오버라이드 표면을 문서화한다. 가져올 세부 기법: Semi의 RGB 채널 팔레트(rgba(var(--x), a) 합성으로 dim 계열 토큰 수 절감), Semi의 층위 서수 토큰(bg-0~4로 페이지/카드/모달/토스트 명도 관리), antd-mobile의 타입 계약된 인스턴스 변수 탈출구.

3. Variant 문법: 축은 직교로, 값은 의미로

Button의 실측 축을 비교하면 성공과 실패 패턴이 갈린다.

시스템Button 축평가
Semitype(의미 5) × theme(강도 4) × size(3)의미와 강도를 직교 분리. 2축으로 20조합
VKUImode(위계 5) × appearance(색 의미 6) × size(3)같은 직교 철학. appearance에 overlay 같은 특수값 포함
antd-mobilecolor(5) × fill(3) × size(4) × shape(3)직교 4축 + Promise 자동 로딩(loading='auto')
Seedvariant 7값(brandSolid, criticalSolid, ghost 등) × size(4) × layout(2)tone × 강도를 7개 합성값으로 제한. JSDoc에 사용 규칙 명시
Primervariant(5) × size(3), IconButton은 별도 컴포넌트축을 동결하고 용도는 컴포넌트로
Mantinevariant(시각 톤 8) × color(자유) × size(10)유연하나 danger조차 color 조합에 위임, 의미 축 부재
ABC Defvariant(6) × size(10!) × rounded(5)size 10종은 아이콘 변형까지 한 축에 뭉친 결과
Base Webkind(6: 강조×danger 뭉침) × shape(7) × size(신구 공존 7)반면교사: 의미와 강조를 한 축에 뭉치면 값이 폭발하고, 네이밍 실패가 영구 이월된다
권고. primitive 버튼은 tone(brand | neutral | critical) × variant(solid | weak | outline | ghost) × size(3~4)의 직교 3축으로 시작한다. Base Web의 kind 뭉침과 size 신구 공존이 보여주듯, 축 설계 실패는 되돌릴 수 없는 이월 비용이 된다. Seed처럼 조합 전부를 열지 말고 유효 조합만 화이트리스트로 노출하는 것도 좋다(7값 제한 + JSDoc 사용 규칙). 색 계산은 Mantine의 variantColorResolver처럼 (tone, variant) → 색 4종을 반환하는 중앙 함수 1개로 처리한다. variant 추가가 컴포넌트 N개 수정이 아니라 함수 분기 1개가 된다.

4. Use-case 계층: 8개 시스템이 그리는 스펙트럼

"용도를 어디까지 시스템이 소유하는가"에서 8개 시스템은 하나의 스펙트럼에 놓인다.

순수 primitive Mantine variant는 전부 시각 톤. 용도 개념 자체가 없다. danger도 color="red" 조합.
프리셋 배선 ABC Def · antd-mobile AlertDialogAction = Button(variant=default) 고정 래퍼. DialogActionButton도 동일. primitive는 오염되지 않는다.
용도 컴포넌트 승격 Primer · Semi · Base Web · VKUI ConfirmationDialog, Modal.confirm, ButtonTimed, PanelHeaderSubmit. 용도가 이름이 된 별도 컴포넌트.
use-case가 기본형 Seed 범용 Button이 없다. ActionButton, ReactionButton, FieldButton부터 시작. 도메인 컴포넌트(MannerTemp)까지 시스템이 소유.

실측에서 확인된 핵심 사실:

  • Seed조차 use-case를 variant 축으로 풀지 않았다. ActionButton과 ReactionButton은 별도 컴포넌트고, 한 컴포넌트의 variant 축은 3개 이하로 유지한다.
  • VKUI는 직교 primitive(Button)와 용도 컴포넌트(PanelHeaderSubmit, CellButton, WriteBar)가 충돌 없이 공존함을 보여준다. 예외적 용도 variant는 오버레이 아이템(ActionSheetItem destructive | cancel)에만 허용한다.
  • antd-mobile의 ErrorBlock(status: default | disconnected | empty | busy)과 Result(5종)는 상태 화면 자체를 use-case 컴포넌트로 만든 사례다.
권고: 3층 구조.
L1 primitive: 직교 축만 갖는 범용 컴포넌트(Button, Input, Popup, List). Mantine, VKUI 방식.
L2 use-case 컴포넌트: 용도가 이름에 박힌 컴포넌트. L1을 합성하고 프리셋을 배선한다. 예: ConfirmButton(=Button tone=brand solid 고정), DestructiveSheetItem, EmptyState, PageError. Seed의 "컴포넌트 분리, 축 3개 이하, JSDoc 사용 규칙" 원칙을 따른다.
L3 도메인 패턴: 제품 고유 컴포넌트(Seed의 MannerTemp 상당). DS 패키지에 두되 별도 네임스페이스로 격리한다.
범용 Button을 없애는 Seed 방식은 도메인 어휘가 이미 확립된 조직에 맞다. 신규 제품은 L1을 유지하고 L2를 빠르게 늘리는 쪽이 재작업 위험이 작다.
Seed 87개 컴포넌트를 이 프레임으로 전수 분류한 자료: seed-component-tiers.md (L1 40 : L2 44 : L3 3)
후속 실측: variant 와 compound 의 사용 경계, 11개 시스템 → variant-vs-compound.html

5. 모바일 웹뷰 필수 기반: 3사가 수렴한 것

antd-mobile, Seed, VKUI가 서로 참조 없이 같은 결론에 도달한 항목이다. 논쟁 없이 채택한다.

기반구현 지침출처
safe-area 정규화 env(safe-area-inset-*)를 전역 CSS 변수 1곳에서 래핑한다. 하단 고정 컴포넌트(TabBar, Sheet, Snackbar, FAB)가 그 변수를 소비하고 기본 내장한다. 네이티브 쉘이 inset을 이미 처리하는 화면용 끄기 변수를 둔다. Seed(--seed-safe-area-*), VKUI(constants.css), antd-mobile(safeArea:true 기본 + --adm-safe-area-multiple)
pressed 1급, hover 봉인 눌림 피드백은 :active와 -pressed 토큰으로 설계한다. hover는 @media (hover: hover) 가드 아래에만 두고, 생 :hover는 lint로 금지한다. tap-highlight도 전역에서 제거한다. Seed(engaged 셀렉터), antd-mobile(:hover 0건), Base Web(hover 가드), Mantine(hover mixin)
정적 CSS + CSS 변수 + html 속성 테마 런타임 CSS-in-JS 없이 빌드 타임 CSS를 배포한다. 다크 모드와 브랜드 전환은 html data 속성이 CSS 변수를 재정의한다. FOUC 방지 부트 스크립트를 제공한다. antd-mobile, Seed(qvism), VKUI, Primer, Mantine 공통. 반례는 Base Web(Styletron)뿐
오버레이 혈통 Mask → Popup(위치) → 목적별 오버레이(BottomSheet, ActionSheet, Dialog) 순서로 상속 구조를 만든다. 스크롤 잠금과 포탈과 포커스 관리를 밑층 1곳에 둔다. 최상위에 Dialog.confirm() 같은 Promise 명령형 API를 얹는다. antd-mobile(Mask→Popup→Dialog), Mantine(ModalBase 인프라), Seed(목적별 4종 + ResponsiveDialog 어댑터)
터치 타깃 44px+ 기본 컨트롤 높이를 44px 이상으로 끊는다. 시각 크기를 줄여야 하면 Base Web의 minHitArea처럼 가상 요소로 히트 영역만 확장한다. 데스크톱계 스케일(32~36px)을 상속하지 않는다. Primer(coarse 토큰 44px), Base Web(minHitArea 48px), Seed(large 52px)
웹뷰 브리지 대응 테마 부트 스크립트가 웹뷰 브리지(window.webkit.messageHandlers 등)로 플랫폼을 감지하고 html data 속성을 세팅한다. 색 모드 동기화 인터페이스(colorSchemeManager)를 주입식으로 열어 네이티브 설정과 동기화한다. Seed(generateThemingScript), Mantine(colorSchemeManager 인터페이스)

결정이 필요한 항목 1개: 앱 셸 소유권

VKUI는 Epic → Root → View → Panel 계층과 스와이프 백, 스크롤 보존까지 DS가 소유한다. Seed도 stackflow 전용 패키지(AppScreen, AppBar)를 둔다. 웹뷰에서 네이티브 유사 내비게이션을 표준화하는 효과가 가장 크지만, 라우터와 결합된다. 권고: 1단계에서는 AppBar(NavBar)와 TabBar까지만 DS가 소유하고, 화면 전환 스택은 앱 계층에 둔다. 전환 애니메이션 요구가 커지면 VKUI 모델을 재검토한다.
