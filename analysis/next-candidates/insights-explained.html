쉽게 풀어 쓴 해설판

모바일 디자인 시스템, 8개를 뜯어보고 배운 것

원본 보고서 insights.html은 디자인 시스템 8개의 코드를 직접 열어 비교한 기록입니다. 이 문서는 그 내용을 디자인 시스템을 처음 접하는 프론트엔드 개발자와 디자이너 눈높이로 다시 씁니다.

읽는 데 약 20분이 걸립니다. 각 장은 독립적이라 순서 없이 읽어도 됩니다. 깊은 근거가 필요하면 각 장 끝의 접힌 표를 펼치세요.

0장

먼저, 디자인 시스템이 뭔가요?

디자인 시스템은 UI 부품(컴포넌트)을 한 곳에서 만들어 두고, 모든 화면이 가져다 쓰게 하는 부품 창고입니다. 이 문서에서 "부품"과 "컴포넌트"는 같은 말입니다. 부품과 함께 색, 글자 크기, 간격 같은 규칙도 창고에 들어 있습니다.

디자인 시스템이 없으면 화면마다 버튼을 새로 만듭니다. 그러면 화면마다 버튼 색과 높이가 조금씩 달라집니다. 디자인 시스템이 있으면 이렇게 바뀝니다.

// 디자인 시스템이 없을 때: 화면마다 스타일을 직접 씀
<button style="background:#FF6F0F; height:44px; borderRadius:10px">구매하기</button>

// 디자인 시스템이 있을 때: 완성된 부품을 가져다 씀
import { Button } from "@our-company/design-system";
<Button tone="brand" size="large">구매하기</Button>

이번 조사는 무엇을 했나

새 디자인 시스템을 만들기 전에, 이미 검증된 시스템 8개를 골라 공개된 코드를 직접 열어서 비교했습니다. 홍보 문서를 읽은 것이 아닙니다. 코드에서 셀 수 있는 것(특정 코드가 몇 번 나오는지, 버튼 높이가 몇 px인지)을 세었습니다. 원본 보고서는 이것을 "소스 실측"이라고 부릅니다.

결론 요약

보고서의 결론은 세 문장입니다

1. "모바일 지원"이라고 말하는 시스템 8개 중, 코드까지 진짜 모바일인 시스템은 3개뿐이었다. antd-mobile, Seed, VKUI입니다. 나머지는 데스크톱 기준으로 만들어져 있었습니다. 판단은 문서가 아니라 코드로 해야 합니다. (1장)

2. 버튼 같은 부품의 옵션은 "서로 독립인 축 몇 개"로 설계하는 것이 8개 시스템의 공통 답이었다. 그리고 "확인 버튼"처럼 용도가 정해진 부품은 옵션이 아니라 별도 부품으로 만듭니다. (3장, 4장)

3. 모바일 시스템 3개가 서로 베끼지 않았는데도 똑같이 도달한 기반 5가지가 있다. 서로 모르는 팀들이 같은 답을 냈다면, 그 답은 검증된 것입니다. 새 시스템은 이 5가지를 고민 없이 채택합니다. (5장)

1장

"모바일 지원"이라는 문서를 믿지 말고, 코드를 보세요

많은 디자인 시스템이 문서에 "모바일 대응"이라고 씁니다. 그런데 코드를 열어 보면 사실이 아닌 경우가 있었습니다. 조사에서는 코드에서 직접 셀 수 있는 신호 5가지로 판정했습니다. 하나씩 보겠습니다.

신호 1. safe-area를 처리하는가

용어: safe-area

요즘 폰은 화면 위에 카메라 구멍(노치)이 있고, 아래에 홈 표시줄이 있습니다. 그 영역을 피한 "안전한 영역"이 safe-area입니다. CSS에서 이렇게 읽습니다.

/* 홈 표시줄 높이만큼 아래 여백을 확보 */
padding-bottom: env(safe-area-inset-bottom);

신호 2. hover에 기대는가, pressed를 챙기는가

용어: hover와 pressed

hover는 마우스 커서를 올려둔 상태입니다. pressed는 손가락이나 마우스로 누르고 있는 순간입니다. 손가락에는 "올려두기"가 없으므로, 모바일에는 hover가 존재하지 않습니다.

.button:hover  { ... }  /* 마우스 전용. 폰에서는 발동하지 않거나 오작동 */
.button:active { ... }  /* 누르는 순간. 폰에서도 동작 */

신호 3. 기본 버튼 높이가 44px 이상인가

손가락 끝이 화면에 닿는 면적은 지름 약 10mm, 화면 픽셀로 약 38px입니다. 그래서 Apple과 Google 모두 누를 수 있는 요소는 최소 44px 안팎을 권장합니다. 이 크기를 "터치 타깃"이라고 부릅니다. 아래는 실물 크기입니다. 폰에서 이 문서를 열었다면 직접 눌러 보세요.

신호 4와 5. 터치 제스처와 모바일 전용 부품이 있는가

나머지 두 신호는 "모바일에서만 필요한 것을 시스템이 직접 만들어 두었는가"입니다.

  • 터치 제스처: 당겨서 새로고침, 밀어서 삭제 같은 손가락 동작. 데스크톱용 시스템에는 이 코드 자체가 없습니다.
  • 모바일 전용 부품: 바텀시트, 액션시트, 탭바처럼 폰 화면에만 있는 부품. 아래 그림이 그 세 가지입니다.

2장

토큰: 색과 크기에 이름을 붙이는 기술

버튼 색을 코드에 #FF6F0F라고 직접 쓰면 두 가지 문제가 생깁니다. 브랜드 색이 바뀌면 수백 곳을 고쳐야 합니다. 다크 모드에서는 다른 값이 필요한데 분기할 방법이 없습니다. 그래서 모든 디자인 시스템은 값에 이름을 붙여서 씁니다. 이 이름 붙인 값이 토큰입니다.

용어: 디자인 토큰(design token)

색, 크기, 간격 같은 디자인 값에 붙인 이름입니다. 코드에서는 주로 CSS 변수로 구현합니다.

:root { --bg-brand-solid: #FF6F0F; }   /* 이름을 선언 */
.button { background: var(--bg-brand-solid); }  /* 이름으로 사용 */

8개 시스템 전부, 이름을 3단계로 붙입니다

조사한 8개 시스템은 만든 곳도 언어도 다른데, 토큰 구조는 전부 같은 3단계였습니다.

왜 굳이 3단계일까요? 바꿀 때 편하기 때문입니다. 브랜드 색 교체는 팔레트 1곳만 고칩니다. "위험 버튼의 배경을 더 연하게"는 시맨틱 1곳만 고칩니다. "우리 서비스에서만 버튼을 다르게"는 컴포넌트 토큰만 덮어씁니다. 각 요구가 각자의 층에서 끝납니다.

다크 모드는 토큰 값만 바꿉니다

토큰을 쓰면 다크 모드가 간단해집니다. 컴포넌트 코드는 그대로 두고, 토큰의 값만 통째로 바꿉니다.

html { --bg-page: #FFFFFF; --text-main: #222222; }
html[data-theme="dark"] { --bg-page: #17171B; --text-main: #E6E9EC; }

시스템들이 갈린 지점: 눌림 색을 어디에 두는가

3단계 구조는 8개 모두 같았습니다. 차이는 눌렀을 때의 색을 누가 정하느냐였습니다. 모바일 우선 시스템인 Seed는 시맨틱 토큰을 만들 때부터 눌림 색을 짝으로 함께 만듭니다.

--bg-brand-solid:         #FF6F0F;  /* 평상시 */
--bg-brand-solid-pressed: #D95A00;  /* 눌림. 항상 짝으로 존재 */

이 문서의 3장 버튼 데모도 이 방식으로 만들었습니다. 버튼을 눌러 보세요.

반대로 데스크톱 판정을 받은 ABC Def에는 hover용 색만 있고 눌림용 색이 아예 없었습니다. 토큰 사전에 눌림이 없으면, 부품을 만드는 사람마다 눌림 색을 즉흥적으로 정하게 됩니다.

새 시스템에 적용할 결정. 3단계 토큰 구조를 쓴다. 시맨틱 토큰은 Seed처럼 눌림 색을 짝으로 내장한다. hover용 토큰은 만들지 않는다. 스타일 배포는 이렇게 한다: 빌드 시점에 CSS 파일을 미리 만들고, 색은 CSS 변수로 열어 두고, 다크 모드는 html 속성으로 전환한다.

3장

버튼 종류가 폭발하지 않게, 옵션을 축으로 나누기

버튼 하나에도 종류가 많습니다. 주황 강조 버튼, 회색 보조 버튼, 빨간 삭제 버튼, 테두리만 있는 버튼. 이 종류를 어떻게 정리하느냐가 이번 장의 주제입니다. 디자인 시스템은 이 "부품의 종류 옵션"을 variant라고 부릅니다.

주의: 업계에서는 variant를 두 가지로 씁니다. 옵션 전반을 부르는 일반 용어이기도 하고, 특정 옵션 축의 이름이기도 합니다. 이 문서에서 축 이름 variant는 "칠하는 강도" 축을 가리킵니다. 아래 그림에서 확인할 수 있습니다.

실패하는 방법부터 보겠습니다. 종류가 생길 때마다 이름을 하나씩 추가하는 방식입니다.

오른쪽 방식의 축 두 개를 실제 버튼으로 만들면 이렇게 됩니다. 모든 버튼을 직접 눌러 보세요. 눌림 색(2장의 pressed 토큰 짝)이 전부 준비되어 있습니다.

색 계산은 함수 한 곳에 모읍니다

위 매트릭스에서 버튼 한 칸은 색 4가지가 필요합니다. 배경, 글자, 테두리, 눌림 배경입니다. 이 계산을 버튼, 태그, 알림 배너 등 부품마다 따로 하면 금방 어긋납니다. Mantine이 좋은 선례를 보여 줍니다. (tone, variant)를 넣으면 색 4가지를 돌려주는 함수 하나를 두는 방식입니다.

function resolveColors(tone, variant) {
  // 예: ("critical", "outline")

4장

만능 부품과 용도 부품, 두 층으로 나누기

3장의 버튼은 어디에나 쓸 수 있는 만능 부품입니다. 그런데 실제 제품에는 "확인 다이얼로그의 확인 버튼"처럼 용도가 정해진 자리가 반복해서 나옵니다. 이 용도를 시스템이 어디까지 책임질까요? 8개 시스템의 선택이 하나의 스펙트럼 위에 놓입니다.

용어: primitive와 use-case

primitive(프리미티브)는 용도를 정하지 않은 만능 부품입니다. Button, Input이 여기 속합니다. use-case(유스케이스) 컴포넌트는 용도가 이름에 박힌 부품입니다. 보통 primitive에 옵션을 미리 채워서 만듭니다.

// primitive: 옵션이 열려 있음
<Button tone="brand" variant="solid">확인</Button>

// use-case: primitive를 감싸고 옵션을 고정함
function ConfirmButton(props) {
  return <Button tone="brand" variant="solid" {...props} />;
}
만능 부품만 제공 Mantine 용도 개념이 없다. 삭제 버튼도 사용자가 "빨간 버튼"을 조합해서 만든다.
용도 부품이 살짝 ABC Def · antd-mobile 다이얼로그의 확인 버튼 정도만 미리 조합해 둔다.
용도 부품을 정식 제공 Primer · Semi · Base Web · VKUI ConfirmationDialog처럼 용도가 이름이 된 부품이 목록에 정식으로 있다.
용도 부품이 기본 Seed 이름 없는 만능 Button이 없다. 기본 버튼조차 "액션 실행"이라는 용도를 이름에 단 ActionButton이고, 토글과 반응은 별도 부품이다.

파란 테두리가 새 시스템의 권고 위치입니다. 오른쪽 끝의 Seed 방식은 "우리 제품에 어떤 용도가 있는지"를 이미 아는 조직에 맞습니다. 신규 제품은 만능 부품을 유지하는 쪽이 재작업 위험이 작습니다.

권고: 3층으로 쌓는다

L1 · 만능 부품 (primitive)

Button, Input, Popup, List. 3장에서 본 독립 축 옵션만 갖습니다.

L2 · 용도 부품 (use-case)

ConfirmButton, EmptyState(빈 화면), PageError(오류 화면). L1을 감싸고 옵션을 고정합니다. 제품이 크면서 이 층이 계속 늘어납니다.

L3 · 도메인 부품

우리 제품에만 있는 부품. 당근으로 치면 매너온도 표시가 여기입니다. 같은 패키지에 두되 이름 공간(네임스페이스)을 분리해서 섞이지 않게 합니다.

실측에서 확인한 중요한 사실이 하나 있습니다. 용도 부품을 가장 적극적으로 만드는 Seed조차, 용도를 옵션(variant)으로 풀지 않았습니다. "공유용 버튼"이 필요하면 Button에 usage="share" 옵션을 추가하는 것이 아니라, 부품을 새로 만듭니다. 그 덕에 부품 하나의 옵션 축은 3개 이하로 유지됩니다.

원본 근거 보기 (관찰 사례)
  • VKUI는 만능 Button과 용도 부품(PanelHeaderSubmit, CellButton, WriteBar)이 충돌 없이 공존함을 보여 줍니다. 용도 옵션의 예외는 액션시트 항목의 destructive | cancel 하나뿐입니다.
  • antd-mobile의 ErrorBlock(기본, 연결 끊김, 빈 목록, 서버 혼잡 4종)은 "상태 안내 화면" 자체를 용도 부품으로 만든 사례입니다.
  • Seed의 부품 87개를 이 3층으로 분류하면 L1 40개, L2 44개, L3 3개입니다. 상세: seed-component-tiers.md

5장

모바일 3사가 똑같이 도달한 기반 5가지

antd-mobile(중국), Seed(한국), VKUI(러시아)는 서로 참고한 흔적이 없습니다. 그런데 아래 5가지에서 같은 결론에 도달했습니다. 독립적으로 세 번 검증된 답이므로, 새 시스템은 그대로 채택합니다.

기반내용자세히
1. safe-area 전역 처리노치와 홈 표시줄을 피하는 여백을 전역 변수 한 곳에서 정의하고, 하단 부품(탭바, 바텀시트)이 기본으로 사용한다.1장 신호 1
2. 눌림 우선, hover 차단눌림 색을 토큰 짝으로 정식 지원한다. hover는 마우스 환경에서만 켠다.1장 신호 2, 2장
3. 미리 만든 CSS + 변수 테마스타일은 빌드 시점에 CSS 파일로 만든다. 다크 모드는 변수 값 교체로 처리한다.2장
4. 오버레이 상속 구조아래 그림.이 장
5. 터치 타깃 44px 이상기본 버튼 높이를 44px 이상으로 잡는다.1장 신호 3

기반 4. 오버레이는 상속 구조로 만듭니다

용어: 오버레이(overlay)

화면 위에 겹쳐서 뜨는 모든 것입니다. 다이얼로그(확인 창), 바텀시트, 액션시트, 토스트가 전부 오버레이입니다.

오버레이는 종류가 많지만, 공통 숙제는 같습니다. 뒤 화면을 어둡게 하기, 뒤 화면의 스크롤 잠그기, 키보드 초점을 안에 가두기. 이 숙제를 오버레이마다 따로 풀면 품질이 제각각이 됩니다. 모바일 3사는 모두 공통 숙제를 아래층 한 곳에서 풀고, 위층이 물려받는 구조를 만들었습니다.

추가 항목: 웹뷰는 네이티브 앱과 대화가 필요합니다

웹뷰 화면은 네이티브 앱 안에 들어 있으므로, 앱의 설정을 전달받아야 합니다. 대표 사례가 다크 모드입니다. 폰의 다크 모드 설정은 앱이 알고 있고, 웹뷰는 전달받아야 압니다. 이 전달 통로를 브리지라고 부릅니다.
