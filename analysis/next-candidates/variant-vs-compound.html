Variant vs Compound: 부품을 어디까지 열어줄 것인가

컴포넌트 API를 만드는 방식 5가지를 코드로 먼저 정리하고, 유명 디자인 시스템 11개가 실제로 어느 방식을 언제 쓰는지 소스 코드에서 확인했다.

조사 대상: Radix, shadcn/ui, Ant Design, Base Web(Uber), Primer(GitHub), Mantine, Semi(ByteDance), Ant Design Mobile, Seed(당근), ABC Def(LINE), VKUI(VK) · 2026-08-13

0. 용어부터: 컴포넌트를 여는 방식 5가지

버튼이나 팝업 하나를 팀에 제공할 때, "사용하는 쪽에서 무엇을 바꿀 수 있게 할지"를 정해야 한다. 방식은 크게 5가지다. 아래로 갈수록 사용자의 자유가 커진다고 생각하기 쉽지만, 실제로는 각각 쓰이는 자리가 다르다.

1. variant: 완제품에서 옵션만 고르기

비유: 자동차 주문. 색상과 트림은 고르지만 문 위치는 못 바꾼다.

<Button tone="brand" size="large">결제하기</Button>
<Button tone="critical" size="small">삭제</Button>

정해진 선택지(enum) 중에서 고르기만 한다. 내부 구조는 못 건드린다. 선택지가 닫혀 있으니 어느 화면에서든 모양이 같다. 대신 선택지에 없는 요구가 오면 막힌다.

2. slot prop: 정해진 자리에 내용물 하나 끼우기

비유: 액자. 틀은 고정이고 사진만 갈아 끼운다.

<Cell before={<Avatar />} after={<ArrowIcon />}>
  홍길동
</Cell>

"왼쪽 자리", "오른쪽 자리"처럼 위치가 정해진 구멍에 원하는 것을 하나 넣는다. 자리는 시스템이 정하고 내용물만 사용자가 정한다.

3. compound: 부품을 직접 조립하기

비유: 레고. 부품 세트를 받아서 배치를 내가 정한다.

<Dialog>
  <Dialog.Title>정말 삭제할까요?</Dialog.Title>
  <Dialog.Body>삭제하면 되돌릴 수 없어요.</Dialog.Body>
  <Dialog.Footer>
    <Button tone="critical">삭제</Button>
  </Dialog.Footer>
</Dialog>

Title, Body, Footer 같은 부품을 사용자가 직접 넣고 뺀다. 순서를 바꾸거나 부품을 생략할 수도 있다. 자유롭지만, 팀마다 다르게 조립하면 화면이 제각각이 될 위험이 있다. 이 문서의 핵심 질문이 바로 이 위험을 다룬다.

4. config: 목록표를 제출하면 시스템이 그려주기

비유: 식당 예약 명단. 명단만 넘기면 자리는 식당이 배치한다.

<Tabs
  items={[
    { key: 'home', title: '홈' },
    { key: 'chat', title: '채팅' },
    { key: 'my',   title: 'MY' },
  ]}
/>

부품 대신 데이터 배열을 넘긴다. 그리는 일은 전부 컴포넌트가 한다. 조립 자유는 없지만, 컴포넌트가 "전체가 몇 개인지"를 알 수 있어서 밑줄 애니메이션이나 키보드 이동 같은 계산이 쉬워진다.

5. imperative: 함수 한 번 호출하기

비유: 벨 누르기. 마크업을 쓰는 게 아니라 요청 한 번으로 끝낸다.

const ok = await Dialog.confirm({ title: '정말 삭제할까요?' });
if (ok) remove();

토스트나 확인 알럿처럼 "이벤트가 생겼을 때 잠깐 떴다 사라지는 것"은 화면에 미리 그려두는 게 아니라 함수로 호출한다.

1. 무엇이 고민이었나

variant는 안전하다. 선택지가 닫혀 있으니 일관성이 저절로 지켜진다. 대신 확장이 막힌다.

compound는 자유롭다. 어떤 요구든 조립으로 풀 수 있다. 대신 "아무렇게나 조립된 화면"을 막을 방법이 없어 보인다.

그래서 질문은 2개였다.

  1. 잘 만든 시스템들은 언제 variant로 닫고, 언제 compound로 여는가?
  2. compound로 열면 일관성은 정말 포기해야 하는가?

조사 방법: 11개 시스템의 소스 코드를 병렬 에이전트 11개가 직접 읽고, 컴포넌트마다 어느 방식을 쓰는지 세었다. 모든 주장에 소스 파일과 줄 번호 근거가 있다(마지막 장의 접힌 표 참고).

2. 발견 1: 기준은 "상자 개수"다

11개 시스템이 거의 만장일치로 같은 규칙을 따르고 있었다. 컴포넌트의 지위나 계층이 아니라 생김새가 기준이다.

  • 화면에서 한 덩어리로 보이는 것(버튼, 뱃지, 태그, 스위치)은 variant로 닫는다. 실제로 Button은 11개 시스템 전부가 부품 없는 단일 상자 + 옵션 선택형이었다. 예외가 하나도 없었다.
  • 안에 구역이 나뉘는 것(다이얼로그의 제목/본문/버튼줄, 리스트의 행, 폼 필드의 라벨/입력/에러문구)은 compound로 연다. 구역마다 들어갈 내용은 화면마다 다르므로, 시스템이 미리 다 정할 수 없기 때문이다.
한 줄 규칙: 상자가 1개면 옵션 선택(variant), 협조하는 부품이 여럿이면 조립(compound). "버튼인데 조립식으로 만들까?"라는 고민은 하지 않아도 된다. 아무도 그렇게 안 한다.

3. 발견 2: 목록을 그리는 것들은 "목록표(config)"로 닫는 경우가 많다

탭, 셀렉트, 세그먼트 컨트롤, 휠 피커처럼 같은 모양의 항목이 반복되는 컴포넌트는 사정이 다르다.

이런 컴포넌트는 "전체 항목이 몇 개고 지금 몇 번째가 선택됐는지"를 알아야 동작한다. 탭의 밑줄이 미끄러지는 애니메이션, 키보드로 항목 사이를 이동하는 기능, "+3명" 같은 넘침 표시가 전부 그렇다. 부품을 자유 조립으로 열어 두면 부모가 이 정보를 얻기 어렵다. 그래서 목록표(config)로 닫는다.

실제 사고 사례: Ant Design의 유턴. antd는 처음에 탭과 메뉴를 조립식(<Tabs><TabPane>...)으로 열었다. 그런데 위 문제 때문에 v5에서 목록표(items 배열)로 되돌렸고, 옛 방식을 쓰면 경고를 띄우는 호환 코드를 v6인 지금까지 유지하고 있다. 열었다가 닫는 것이 제일 비싸다. 반복 항목형 컴포넌트는 처음부터 목록표로 시작하는 편이 유지비가 낮다.

4. 발견 3: 조립을 열어도 규칙은 지킬 수 있다

"compound는 variant의 제약을 훼손한다"는 걱정은 11개 시스템 전부에서 반증됐다. 잘 만든 시스템은 조립을 열면서 규칙을 지키는 장치를 함께 깐다. 대표 장치 4가지다.

장치 1. 옵션은 부모에서 한 번만 정한다

<Tabs variant="pill">   <!-- 모양은 여기서 한 번만 -->
  <Tabs.Tab>홈</Tabs.Tab>   <!-- Tab에는 variant prop이 아예 없다 -->
  <Tabs.Tab>채팅</Tabs.Tab>
</Tabs>

부품(Tab)의 props에서 모양 옵션을 아예 빼 버린다. 부품은 부모가 정한 모양을 내부 통신(context)으로 전달받아 그대로 따른다. 조립은 자유지만 모양 결정권은 한 곳뿐이다. Mantine과 Seed가 이 방식이다.

장치 2. 그룹 설정이 개별 설정을 이긴다

<ButtonGroup size="small">
  <Button size="large">A</Button>  <!-- large는 무시된다. small로 그려진다 -->
  <Button>B</Button>
</ButtonGroup>

그룹 안에서 하나만 튀는 것을 시스템이 막는다. Uber의 Base Web은 소스 주석에 이유까지 적어 뒀다: "일관성 보장을 위해 그룹 값이 우선한다".

장치 3. 부품을 엉뚱한 곳에 쓰면 즉시 에러

<Dialog.Title>제목</Dialog.Title>
// Error: Dialog.Title must be used within Dialog

부품을 부모 밖에서 단독으로 쓰면 바로 실패시킨다. 잘못된 조립이 화면에 나가기 전에 개발 단계에서 걸린다.

장치 4. 모양만 조립인 "가짜 부품"

<Tabs>
  <Tabs.Tab title="홈" />   <!-- 이 부품은 사실 아무것도 안 그린다 -->
  <Tabs.Tab title="채팅" />
</Tabs>

Ant Design Mobile의 Tabs.Tab은 내부적으로 return null이다. 아무것도 렌더하지 않는다. 부모가 부품들의 정보만 수거해서 화면 전체를 직접 그린다. 사용자는 조립하는 기분을 느끼지만 실제 통제권은 100% 부모에게 있다. 쓰는 맛(JSX 조립)과 일관성(부모 독점)을 동시에 잡는 절충안이고, 모바일 시스템들이 특히 애용한다.

"부품을 노출하는 컴포넌트가 전체의 몇 %인가"를 세어 보면 경향이 뚜렷하다.

6. 그래서 우리 규칙: 질문 5개

새 컴포넌트를 만들 때 위에서부터 순서대로 묻는다. 처음 "예"가 나온 방식을 쓴다.

#질문예라면우리 앱 예시
1이벤트가 생겼을 때 잠깐 떴다 사라지는 것인가?함수 호출토스트, 확인 알럿 Dialog.confirm()
2화면에서 한 덩어리로 보이는가?variantButton, Badge, Chip, Switch
3정해진 자리에 내용물 하나만 받으면 되는가?slot prop리스트 행의 좌우 아이콘(before/after)
4같은 모양 항목이 반복되고, 전체 개수를 알아야 동작하는가?config 목록표TabBar, SegmentedControl, Picker, ActionSheet의 버튼들
5내부 구역의 내용과 유무가 화면마다 다른가?compound + 장치 1~3 장착BottomSheet(제목/본문/버튼줄), 폼 Field, List
덤으로 얻은 공식 (L1/L2 연결). 성숙한 시스템들은 같은 도메인을 두 층으로 판다. 아래층(L1)은 조립형 원형을 열어 두고, 위층(L2)은 그 원형을 미리 조립해서 옵션 선택형으로 닫아 판다. 예: Mantine은 조립형 Combobox 위에 목록표만 받는 Select를 얹었다. 대부분은 Select를 쓰고, 특수한 화면만 Combobox를 꺼낸다. 우리도 L2 use-case 컴포넌트를 이 방식(L1 조립 + 기본값 고정)으로 만들면 두 층을 싸게 얻는다.

7. 상세 실측 자료

여기부터는 근거를 확인하고 싶은 사람용이다. 각 표는 원 소스의 파일:줄 번호를 담고 있다.

가설 판정 전체표: 11개 시스템별 부품 노출 비율과 판정

검증한 원래 가설: "primitive는 compound 위주, 상위 레이어는 variant 위주다". 판정 결과 성립 0, 부분 성립 8, 불성립 3. 가설이 맞는 절반: 동작만 제공하는 headless 층(Radix, Seed headless)은 실제로 compound 극단이다. 가설이 틀리는 절반: 시각적 최소 단위(Button 등)는 전부 variant고, 상위 레이어가 닫는 수단은 variant보다 config가 많다.
