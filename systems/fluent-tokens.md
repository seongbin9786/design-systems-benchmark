#### `alias/darkColor.ts` — Light vs Dark 실제 차이

```ts
export const generateColorTokens = (brand: BrandVariants): ColorTokens => ({
  // Light: grey[14] (#242424) → Dark: white (#ffffff)
  colorNeutralForeground1: white,

  // Light: white (#ffffff) → Dark: grey[16] (#292929)
  colorNeutralBackground1: grey[16],

  // Light: grey[96] (#f5f5f5) → Dark: grey[24] (#3d3d3d)
  colorNeutralBackground1Hover: grey[24],

  // Light: brand[80] → Dark: brand[70] (브랜드도 시프트)
  colorBrandBackground: brand[70],
  colorBrandBackgroundHover: brand[80],

  // Light: brand[80] → Dark: brand[100] (어두운 배경 위 밝은 브랜드)
  colorCompoundBrandForeground1: brand[100],

  // Light: white → Dark: grey[14] (반전)
  colorNeutralForegroundInverted: grey[14],

  // Light: blackAlpha → Dark: grey10Alpha (어두운 배경용 반투명)
  colorNeutralBackgroundAlpha: grey10Alpha[50],

  // Shadow 강화 (어두운 배경에서 그림자 더 진하게)
  colorNeutralShadowAmbient: 'rgba(0,0,0,0.24)',  // Light: 0.12
  colorNeutralShadowKey: 'rgba(0,0,0,0.28)',       // Light: 0.14

  // Focus ring 반전
  colorStrokeFocus1: black,   // Light: white
  colorStrokeFocus2: white,   // Light: black
});
```

**Dark 모드 핵심 패턴**:
1. **명도 반전**: foreground ↔ background 명도 관계 역전
2. **브랜드 시프트**: `brand[80]` → `brand[70]`(배경), `brand[80]` → `brand[100]`(前景) — 어두운 배경에서 대비 확보
3. **Alpha 기반 변경**: `whiteAlpha` → `grey10Alpha`/`grey12Alpha` — 반투명 레이어의 베이스 색상 변경
4. **Shadow 강화**: 그림자 opacity 2배 증가

### 1.5 네이밍 Taxonomy

```
colorNeutralBackground1Hover
│     │       │         │   └─ Interaction State: (rest) | Hover | Pressed | Selected
│     │       │         └─ Variant Index: 1~8 (계층적 배경)
│     │       └─ Role Category: Foreground | Background | Stroke | Shadow
│     └─ Palette Group: Neutral | Brand | CompoundBrand | Subtle | Transparent
└─ Token Type: color | fontSize | fontWeight | lineHeight | fontFamily |
               spacingHorizontal | spacingVertical | borderRadius |
               strokeWidth | duration | curve | shadow
```

**Color Palette 네이밍**:
```
colorPaletteRedBackground3
│     │       │   │         └─ Slot: Background1~3 | Foreground1~3 | Border1~2 | BorderActive
```

### 1.6 Component-level 토큰 계층이 없는 이유

**Fluent의 설계 결정**: MD3의 `md-comp-button-container-color` 같은 컴포넌트 전용 토큰 계층이 **존재하지 않는다**.

**대신 사용하는 패턴**:

```ts
// useButtonStyles.styles.ts에서 alias 토큰을 직접 참조
backgroundColor: tokens.colorNeutralBackground1,        // 범용 alias
':hover': {
  backgroundColor: tokens.colorNeutralBackground1Hover, // 범용 alias (hover variant)
},
```

**이유 분석**:
1. **Alias 토큰 자체가 충분히 시맨틱**: `colorBrandBackground` + `Hover`/`Pressed` 상태 variant가 이미 컴포넌트 사용 맥락을 인코딩
2. **Griffel atomic CSS**: 스타일이 컴포넌트 파일에 co-locate되므로, 별도 component token 추상화 계층이 불필요
3. **토큰 폭발 방지**: 50개 컴포넌트 × 10개 속성 × 4개 상태 = 2,000개 component token 대신, 184개 alias token 재사용
4. **테마 일관성**: 모든 컴포넌트가 동일 alias를 참조하므로, alias 값 변경 시 전체 UI 일관성 자동 보장

**트레이드오프**: 특정 컴포넌트의 특정 속성만 override하려면 `Partial<Theme>`으로 alias 자체를 바꿔야 하며, 이는 **모든 컴포넌트에 영향**. MD3의 component token은 이 점에서 더 세밀한 제어 가능.

## 2. Token Consumption (소비)

### 2.1 FluentProvider의 CSS Custom Properties 주입

#### 주입 메커니즘

```
FluentProvider (theme prop)
  → useFluentProviderThemeStyleTag()
    → createCSSRuleFromTheme(selector, theme)
      → "<style> .fui-FluentProvider-xxx { --colorNeutralBackground1: #ffffff; ... } </style>"
```

#### `createCSSRuleFromTheme.ts` — 실제 코드

```ts
export function createCSSRuleFromTheme(selector: string, theme: PartialTheme | undefined): string {
  if (theme) {
    const cssVarsAsString = (Object.keys(theme) as (keyof typeof theme)[]).reduce((cssVarRule, cssVar) => {
      return `${cssVarRule}--${cssVar}: ${theme[cssVar]}; `;
    }, '');
    return `${selector} { ${escapeForStyleTag(cssVarsAsString)} }`;
  }
  return `${selector} {}`;
}
```

**결과**: 테마 객체의 **모든 키**가 `--camelCaseName: value;` 형태의 CSS custom property로 변환되어 `<style>` 태그로 DOM에 주입.

#### `useFluentProviderThemeStyleTag.ts` — 실제 주입 로직

```ts
export const useFluentProviderThemeStyleTag = (options) => {
  const { targetDocument, theme, rendererAttributes } = options;
  const styleTagId = useId(fluentProviderClassNames.root);

  // Theme → CSS rule 변환 (메모이제이션)
  const rule = React.useMemo(
    () => createCSSRuleFromTheme(`.${styleTagId}`, theme),
    [theme, styleTagId]
  );

  // React.useInsertionEffect로 DOM 주입 (React 18+)
  useInsertionEffect(() => {
    const ssrStyleElement = targetDocument?.getElementById(styleTagId);
    if (ssrStyleElement) {
      styleTag.current = ssrStyleElement;  // SSR 재사용
    } else {
      styleTag.current = createStyleTag(targetDocument, { ...rendererAttributes, id: styleTagId });
      if (styleTag.current) {
        insertSheet(styleTag.current, rule);  // sheet.insertRule()
      }
    }
    return () => { styleTag.current?.remove(); };
  }, [styleTagId, targetDocument, rule]);

  return { styleTagId, rule };
};
```

**핵심**: `React.useInsertionEffect` (React 18) 사용하여 layout 계산 전에 스타일 주입. SSR 시 기존 `<style>` 태그 재사용.

**이중 구조의 의미**:

### 2.3 `themeToTokensObject.ts` — 동적 변환

```ts
export function themeToTokensObject<TTheme extends Theme>(theme: TTheme): Record<keyof TTheme, string> {
  const tokens = {} as Record<keyof TTheme, string>;
  const keys = Object.keys(theme) as (keyof TTheme)[];
  for (const key of keys) {
    tokens[key] = `var(--${String(key)})`;
  }
  return tokens;
}
```

커스텀 테마 사용 시 정적 `tokens` 객체 대신 동적으로 var() 맵 생성. Tree-shaking에 불리할 수 있음을 주석으로 경고.

### 2.6 Griffel 소비 패턴 요약

| Griffel API | 용도 | Token 소비 방식 |
|-------------|------|----------------|
| `makeResetStyles()` | Base layer (모든 variant 공통) | `tokens.colorNeutralBackground1` 등 직접 참조 |
| `makeStyles()` | Variant matrix (appearance/size/shape) | 동일, variant별 다른 alias token 참조 |
| `mergeClasses()` | 런타임 variant 합성 | Token 무관, class 조합 |
| `shorthands.*` | CSS shorthand 전개 | Token 값 전달 (`shorthands.borderColor(tokens.xxx)`) |

**Atomic CSS 생성**: Griffel은 각 CSS declaration을 개별 atomic class로 변환:
```
.f3j1b3r { background-color: var(--colorNeutralBackground1); }
.f1g6xwjb { color: var(--colorNeutralForeground1); }
.f1hc3gag { border-radius: var(--borderRadiusMedium); }
```
→ 동일 token을 사용하는 모든 컴포넌트가 **동일 atomic class 재사용**.

**버전 전략**:
- `@fluentui/tokens` 패키지는 독립 SemVer (현재 9.x)
- Beachball (Microsoft의 changelog/versioning 도구)로 자동 semver bump
- Token 추가 → minor bump, Token 값 변경 → minor bump (v9 내에서는 breaking으로 취급 안 함)
- Token 제거 → major bump (v8 → v9 전환 시 발생)

**변경 영향 범위**: Alias 토큰 값 변경 시 → 해당 alias를 참조하는 **모든 컴포넌트**에 영향. Component-level token이 없으므로 세밀한 영향 범위 제어 불가.

### 3.4 Figma Variables ↔ Code 토큰 동기화

**현재 상태**:

| 항목 | 현황 |
|------|------|
| **네이밍 정합** | Figma Variables와 Code tokens가 동일한 camelCase 네이밍 공유 (`colorNeutralBackground1`) |
| **구조 정합** | Figma도 Global → Alias 2-layer 구조 |
| **Mode 정합** | Figma Variables의 Light/Dark mode ↔ Code의 `webLightTheme`/`webDarkTheme` |
| **자동 sync** | **없음** — Style Dictionary, Tokens Studio, 또는 자체 sync 도구에 대한 공개 문서 부재 |
| **생성 파이프라인** | Code tokens는 "token pipeline"으로 자동 생성되나, 이 파이프라인의 입력 소스(Figma인지 별도 도구인지)는 비공개 |
| **수동 정렬** | 동일 조직(Fluent team)이 Figma Kit과 Code를 함께 유지 → 개념적 정합은 수동으로 보장 |

**증거 분석**:
- `/* This file has been generated by the token pipeline */` — 코드 토큰이 자동 생성됨은 확인
- 그러나 이 pipeline이 Figma Variables를 직접 읽는지, 별도의 디자인 토큰 소스(예: 내부 JSON/YAML)에서 생성하는지는 불분명
- Figma Community에 공개된 Fluent 2 Design Language 파일에 Variables가 존재하나, 이 파일과 코드 간 자동 연결 고리는 공개되지 않음
- **결론**: Figma ↔ Code 동기화는 **조직적 프로세스(동일 팀 소유)에 의존**하며, 기계적 자동 sync 파이프라인은 부재

### 3.5 `@fluentui/tokens` vs `@fluentui/react-theme`

| 패키지 | 역할 |
|--------|------|
| `@fluentui/tokens` | Canonical token 정의 + 테마 팩토리 + 타입. 플랫폼 무관. |
| `@fluentui/react-theme` | React v9 전용 re-export. `tokens` 객체 + 테마 + `createCustomFocusIndicatorStyle` 등 React 유틸 추가. |

컴포넌트는 `@fluentui/react-theme`에서 import:
```ts
import { tokens } from '@fluentui/react-theme';  // useButtonStyles.styles.ts
```

### 4.2 핵심 설계 결정 요약

| 결정 | 내용 | 영향 |
|------|------|------|
| **2-layer (Global→Alias)** | Component token 계층 없음 | 토큰 수 절약(~463), 그러나 컴포넌트별 세밀 override 불가 |
| **Brand as parameter** | `generateColorTokens(brand: BrandVariants)` | 브랜드 색상 16값만 교체하면 전체 테마 재생성 |
| **CSS var() 간접 참조** | 컴포넌트는 `var(--token)` 사용, 실제 값은 Provider 주입 | 테마 교체 시 스타일 재계산 없음, 런타임 전환 가능 |
| **자동 생성** | `/* generated by token pipeline */` | 수동 편집 금지, 파이프라인이 single source of truth |
| **Griffel atomic CSS** | Token → atomic class, 최대 재사용 | 동일 token 사용 시 DOM class 공유, 번들 효율 |
| **High Contrast = 시스템 색상** | 브랜드 완전 제거, OS 키워드만 사용 | Windows 접근성 자동 준수 |
| **Horizontal/Vertical spacing 분리** | 방향별 간격 명시화 | RTL/수직 리듬 독립 제어 |
| **Nudge 단계** | 표준 스케일 사이 미세 값 (6px, 10px) | 아이콘 정렬 등 픽셀 퍼펙트 조정 |

### 4.3 다른 시스템과의 구조적 비교

| 특성 | Fluent 2 | Material Design 3 | Carbon | Polaris |
|------|----------|-------------------|--------|---------|
| Token 계층 | 2 (Global→Alias) | 3 (ref→sys→comp) | 2 (Global→Component) | 2 (Global→Alias) |
| Component token | ❌ 없음 | ✅ `md-comp-*` | ✅ `$button-*` | ❌ 없음 |
| 총 토큰 수 | ~463 | ~300 (sys) + comp | ~1,100+ | ~200+ |
| 테마 분기 | Light/Dark/HC | Light/Dark (+dynamic) | White/g10/g90/g100 | Light/Dark |
| 브랜드 파라미터화 | ✅ `BrandVariants[16]` | ✅ `seed` color | ❌ 고정 | ❌ 고정 |
| CSS 전달 | var() (runtime) | var() / Sass | Sass / CSS vars | CSS vars |
| 자동 생성 | ✅ token pipeline | ✅ (내부) | 부분 | 부분 |
| Figma sync | ❌ 수동 | ❌ 수동 | ❌ 수동 | ❌ 수동 |
